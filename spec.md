# Teamflow — MVP Specification

A team work-tracking app that makes the split between **regular (recurring) work** and **ad-hoc (unplanned) work** a first-class concept, so a team lead can see where capacity actually goes.

This document is the source of truth for the build. `schema.sql` is the companion database migration.

---

## 1. The problem this solves

Most teams run on two kinds of work:

- **Regular work** — recurring, predictable, scheduled. Weekly reports, monthly closes, daily standups, quarterly reviews, routine maintenance. It's known in advance and should be auto-generated, not manually re-created every cycle.
- **Ad-hoc work** — interrupts. Requests from other teams, incidents, "can you just quickly…". Unpredictable, and the main reason planned work slips.

Existing tools track *tasks* well but treat all work as the same shape. The core question this app answers is: **"How much of my team's capacity is being eaten by unplanned work, and who is over capacity this week?"**

Every task therefore carries a mandatory `work_type` of `recurring` or `adhoc`, and the workload views slice by it.

What we deliberately take from each tool, and what we deliberately leave out for MVP.

| **Jira** | Human-readable task keys (`OPS-142`) | Referenceable in Slack/email/standups |
| **Jira** | Workflow statuses grouped into categories (todo / in progress / blocked / done) | Lets each project name its own columns while reporting stays consistent |
| **Jira** | Priority levels + activity history (audit log) | Accountability and triage |

| **Asana** | Recurring task templates that auto-generate instances | This is the backbone of "regular load" |
| **Asana** | Subtasks (one level deep) | Enough structure without a full epic hierarchy |
| **Asana** | Multiple views over the same data (Board / List / My Tasks / Workload) | Different roles need different lenses |

**Explicitly out of MVP:** timeline/Gantt, custom fields, automations/rules engine, guest access, forms intake, file attachments beyond links, mobile app, integrations (Slack/email), portfolio roll-ups, dependencies between tasks.

## 3. Glossary

| Term | Meaning |
|---|---|
| **Workspace** | Top-level container for one team or org. Billing/membership boundary. |
| **Project** | A body of work inside a workspace. Has its own key prefix (`OPS`) and its own columns. |
| **Workflow status** | A column on the board (e.g. "In Review"). Belongs to a project, maps to a `status_category`. |
| **Task** | The unit of work. Always `recurring` or `adhoc`. |
| **Recurrence template** | A blueprint that generates recurring tasks on a schedule. |
| **Capacity** | A person's `weekly_capacity_hours` (default 40). Compared against assigned estimated hours. |
| **Time entry** | Actual hours logged against a task on a date. |

## 4. Data model overview

Fifteen tables. Full DDL is in `schema.sql`.

```
auth.users (Supabase)
   └── profiles                       1:1, capacity + timezone live here
workspaces
   ├── workspace_members              (user ↔ workspace, with role)
   └── projects
        ├── project_members           (optional narrowing; workspace access is the default)
        ├── workflow_statuses         the board columns, ordered, with WIP limits
        ├── labels
        ├── recurrence_templates      ──generates──┐
        └── tasks  ◄─────────────────────────────-─┘
             ├── tasks (self-FK: parent_task_id, one level of subtasks)
             ├── task_labels          (m:n join)
             ├── task_checklist_items
             ├── task_comments
             ├── time_entries
             └── task_activity        append-only audit log
```

### Key design decisions

1. **`work_type` is `not null` on `tasks`.** No default in the UI — the user must choose. This is the whole point of the app; letting it default would let it rot.
2. **Task keys are generated by trigger.** `projects.task_counter` is incremented atomically; `tasks.ref` becomes `OPS-142`. Unique per project.
3. **Ordering uses a sparse numeric `position`.** New cards get `max(position) + 1024`; drag-and-drop sets position to the midpoint of its neighbours. Avoids reindexing every row on every drag.
4. **Status is a FK to `workflow_statuses`, not an enum.** Each project defines its own columns. Reporting joins to `status_category` so it stays comparable across projects.
5. **Recurring tasks are *materialized*, not virtual.** The generator creates a real `tasks` row per occurrence, linked back via `recurrence_template_id`. This means a recurring task can be reassigned, re-estimated, commented on, and completed like any other — and it shows up in workload math for the week it lands in.
6. **Load is computed from `estimate_hours`,** bucketed into the ISO week of `due_date` (falling back to `start_date`, then `created_at`). `time_entries` gives you actual-vs-estimate later.
7. **RLS everywhere,** driven by workspace membership via a `security definer` helper function (avoids infinite recursion in the policy on `workspace_members` itself).

## 5. Core workflows

### 5.1 Recurring task generation

- A `recurrence_template` defines: title, description, project, default assignee, estimate, priority, and a schedule (`frequency` + `interval` + `byweekday[]` / `bymonthday`).
- `lead_time_days` controls how far ahead the instance appears (e.g. generate the Monday report task the preceding Thursday).
- A generator runs daily (Supabase scheduled Edge Function, or a Vercel cron hitting an API route). For each active template where `next_run_at <= now()`:
  1. Insert a `tasks` row with `work_type = 'recurring'`, `recurrence_template_id` set, `due_date` = the occurrence date, status = the project's first `todo` column.
  2. Advance `next_run_at` to the following occurrence.
- **Idempotency:** unique index on `(recurrence_template_id, due_date)` so a double-run can't create duplicates.
- Pausing a template (`is_active = false`) stops future generation but leaves existing tasks alone.

### 5.2 Ad-hoc intake

- "New task" defaults to a board column but forces a `work_type` choice.
- Ad-hoc tasks additionally capture `requested_by` (free text or a member) and `source_note` — where the interrupt came from. This is what makes the ad-hoc report actionable ("40% of our ad-hoc load comes from Sales requests").
- Ad-hoc tasks are visually distinct on the board (accent border / badge).

### 5.3 Load calculation

For a given person and ISO week:

```
planned_hours   = Σ estimate_hours of non-archived, non-done tasks assigned to them
                  whose bucket week = that week
recurring_hours = same, filtered to work_type = 'recurring'
adhoc_hours     = same, filtered to work_type = 'adhoc'
capacity        = profiles.weekly_capacity_hours
utilization     = planned_hours / capacity
adhoc_ratio     = adhoc_hours / planned_hours
```

The Workload view renders one row per person, one column per week (default: next 6 weeks), with a stacked bar of recurring vs ad-hoc against a capacity line. Over 100% turns red.

## 6. Screens and routes

| Route | Screen | Contents |
|---|---|---|
| `/login` | Auth | Supabase email/password + magic link |
| `/` | Workspace home | Project cards, "my open tasks" count, this week's utilization |
| `/projects/[id]/board` | **Board (default)** | Kanban columns from `workflow_statuses`, drag-and-drop, WIP limit warnings, filter bar (assignee / work_type / priority / label) |
| `/projects/[id]/list` | List | Flat sortable table: ref, title, type, assignee, due, estimate, status |
| `/projects/[id]/recurring` | Recurring templates | CRUD for templates, next occurrence preview, pause/resume |
| `/projects/[id]/settings` | Project settings | Name, key, columns (add/rename/reorder/WIP), labels, members |
| `/my-tasks` | My Tasks | Everything assigned to me across projects, grouped Overdue / Today / This week / Later |
| `/workload` | **Workload** | Per-person × per-week grid, recurring vs ad-hoc stacked, capacity line, week range picker |
| `/reports` | Reports | Ad-hoc ratio trend over time, completed-vs-created, load by project |
| `/tasks/[ref]` | Task detail (modal over board, deep-linkable) | Description, subtasks, checklist, labels, comments, time log, activity history |

## 8. Build order

Build and verify in this order. Do not start a milestone until the previous one runs locally.

**M0 — Foundation**
Scaffold Next.js + Tailwind + Supabase client. Run `schema.sql`. Generate TS types. Auth: sign up, log in, log out, protected layout. Auto-create a `profiles` row on signup via trigger.
*Done when:* I can sign up, land on an empty home page, and refresh without losing session.

**M1 — Workspaces & projects**
Create workspace on first login. Invite members by email. Create a project (name + key). Auto-seed four default `workflow_statuses` (Backlog / In Progress / In Review / Done) on project creation.
*Done when:* Two users in the same workspace both see the same project list, and a user outside it sees nothing (verify RLS by querying as the other user).

**M2 — Tasks & board**
Create/edit/delete tasks. `work_type` is a required toggle in the create form. Board renders columns from `workflow_statuses`. Drag-and-drop between and within columns persists `status_id` + `position`. Task detail modal, deep-linkable by `ref`.
*Done when:* I can drag a card, hard-refresh, and it's still where I left it.

**M3 — The details that make it usable**
Labels, priority, assignee picker, due date, `estimate_hours`, subtasks (one level), checklist items, comments. Filter bar on the board. Overdue styling.
*Done when:* A card can be fully described without touching the database.

**M4 — Recurring work**
Recurrence template CRUD. `computeNextOccurrence()` with unit tests for daily / weekly-by-weekday / monthly-by-day / quarterly, including month-end edge cases (31st in February). The `/api/cron/generate-recurring` route. Wire up the schedule.
*Done when:* I create a "every Monday" template, manually hit the cron endpoint twice, and get exactly one task — not two.

**M5 — Workload & reports**
Capacity editing on the profile. Workload grid: people × weeks, stacked recurring vs ad-hoc, capacity line, over-capacity highlighting. Ad-hoc ratio trend on `/reports`.
*Done when:* Assigning a 20-hour ad-hoc task visibly moves someone's bar past their capacity line.

**M6 — Polish & ship**
Time entries + actual-vs-estimate. Realtime board sync via Supabase channels. Empty states, loading skeletons, error boundaries. Seed script with realistic demo data. Deploy to Vercel with production Supabase.

## 9. Non-negotiables

- **RLS on every table**, no exceptions. Test each policy by querying as a non-member — do not assume it works because the UI hides it.
- **Never use the Supabase service-role key in client code.** It belongs only in the cron route's server environment.
- `.env.local` in `.gitignore` from the very first commit.
- All writes go through typed functions in `/lib/queries`, validated with Zod. No inline Supabase calls scattered through components.
- `git commit` at the end of every milestone, with a message naming the milestone.
- Seed data must include both recurring and ad-hoc tasks across at least three people and four weeks, or the workload view can't be evaluated.
